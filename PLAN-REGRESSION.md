# Cross-engine pairing regression analysis

A plan for running this repository's test corpus through an independent FIDE
Dutch pairing engine and analysing where the two disagree.

The first — and for now the only — comparison engine is
[bbpPairings](https://github.com/BieremaBoyzProgramming/bbpPairings) v6.0.0. The
design keeps the engine behind an interface so a second one (JaVaFo, say) is a
new module and a registry line, not a rewrite. Nothing in the corpus loader, the
truncation transform, the normalisation, the classification or the report is
specific to bbpPairings.

FIDE team pairing (C.04.6) is out of scope: no independent implementation is
known to exist, and bbpPairings rejects team tournaments outright.

## 1. Why this is worth building

`tests/corpus/README.md` records that the corpus fixtures were generated by this
engine. Their `valid` flags are therefore this engine's own opinion, restated.
That makes the corpus excellent at catching a *regression* — a change that moves
the engine away from where it was — and structurally incapable of catching a
*standing misreading* of C.04.3 that the engine has held all along, because the
fixture and the engine agree by construction.

bbpPairings is the first genuinely independent oracle that can be pointed at
these 5,000 individual tournaments. Every divergence it reports is information
the existing suite cannot produce, whichever engine turns out to be wrong.

### 2.2 What bbpPairings v6.0.0 reads

From `src/fileformats/trf.cpp` at tag `v6.0.0`. It targets **TRF-2026**, the
same dialect this corpus emits.

Records handled: `001 012 013 142 152 162 192 240 250 260 299 310`,
`XXA XXC XXP XXR`, and the `BBW/BBD/BBL/BBZ/BBF/BBU` point-system extension.
**Unknown record prefixes are silently ignored**, which is what makes the
corpus's `062 072 182 212` records harmless.

It rejects three things outright, each with a distinct message:

| trigger | message |
|---|---|
| record `013` or `310` | `team tournaments are not supported` |
| record `299` | `abnormal assignment points are not yet supported` |
| record `192` outside its accepted set | `unsupported tournament type` |

The accepted `192` values in **v6.0.0** are `FIDE_DUTCH`, `FIDE_DUTCH_2025`,
`FIDE_DUTCH_BAKU`, `FIDE_DUTCH_2025_BAKU`, `FIDE_BURSTEIN`,
`FIDE_BURSTEIN_BAKU`. Note that `FIDE_DUTCH_2026` and `FIDE_DUTCH_2026_BAKU`
were added *after* the release and are **not** accepted by the pinned binary.
This corpus writes `FIDE_DUTCH_BAKU`, which is accepted — but a future corpus
regeneration that switched to the `_2026` spelling would break the sweep against
this pin. Worth a comment in the corpus generator.

Two further capabilities matter and are present:

- **Baku acceleration (C.04.7) is implemented natively** (`applyBakuAcceleration`),
  triggered by the `_BAKU` tournament types.
- **Record 260 prohibited pairings is implemented** (`readForbiddenPairs260`).

One constraint shapes the design: bbpPairings **verifies that each player's
declared score reconciles with their results** under the file's point system and
refuses to proceed when it does not. Any transformation applied to a fixture
must keep scores consistent. This is the reason §5 recomputes the points field.

### 2.3 Command-line surface

```
bbpPairings.exe --dutch INPUT -p [OUTPUT] [-l CHECKLIST]   # pair the next round
bbpPairings.exe --dutch INPUT -c        [-l CHECKLIST]     # check every round
```

`-p` writes a JaVaFo-style pairing file: a count line, then one `WHITE BLACK`
line per board in the engine's own board order, with `0` as the opponent for the
pairing-allocated bye.

```
6
1 12
13 2
...
7 0
```

Exit codes: `0` success, `1` **no valid pairing exists**, `2` unexpected error,
`3` invalid request or malformed input, `4` size limit exceeded, `5` file access
error. Code `1` is a first-class outcome, not a failure — see §4.

`-l` writes a per-player checklist (score, colour preference, float history, and
for the Dutch system the `C2` bye-eligibility flag and `C14`/`C16` float
directions). It is not part of the comparison, but it is the fastest way to
diagnose *why* a divergence happened, so the runner should retain it for
divergent cases only.

### 2.4 Corpus fit, measured

A scan of `tests/corpus/corpus.jsonl.gz` shows the individual fixtures carry
exactly these record prefixes: `001 062 072 142 152 182 192 212 250 260 299`.

| | fixtures | bbpPairings |
|---|---:|---|
| individual, total | 5,000 | 4,281 valid / 719 invalid |
| `192` absent | 3,414 | accepted |
| `192 FIDE_DUTCH_BAKU` | 1,586 | accepted, native Baku |
| `250` acceleration | 1,586 | accepted |
| `260` prohibited pairings | 536 | accepted |
| **`299` abnormal assignment** | **212** | **rejected — excluded** |
| `062 072 182 212` | all | ignored |

**4,788 of 5,000 individual fixtures (95.8%) are directly consumable.** No
fixture carries record `162`, so the standard point system applies throughout
and bbpPairings' score reconciliation is satisfied without `BBW`/`BBD` lines.
The 1,000 team fixtures are out of scope.

### 2.5 TRF `001` column layout

Verified against `trf2json.py` and against a real fixture. Zero-based Python
slices:

| field | slice |
|---|---|
| starting rank | `line[4:8]` |
| points | `line[80:84]`, written as `f"{points:4.1f}"` |
| rank | `line[85:89]` |
| round *r* (1-based) | `line[81 + 10*r : 89 + 10*r]` |

Within a round block: opponent `[81+10r : 85+10r]`, colour at `86+10r`, result
at `88+10r`. Truncating a player line to the first *k* rounds is
`line[: 89 + 10*k]`.

## 3. What gets compared

**Not the corpus's `valid` flag.** That flag is a joint identity verdict over
both the prescribed pairing *and* the standings produced by the declared
tie-breaks. bbpPairings has no tie-break notion, so the flag is not a quantity
the two engines can both produce. Comparing it would silently conflate a pairing
disagreement with a tie-break one.

**The comparison unit is one `(fixture, round)` pairing decision.** Truncate a
fixture to the results of rounds 1..*k*−1, ask both engines to pair round *k*,
and compare what comes back.

This is the right unit for three reasons:

1. **Volume.** ≈4,788 fixtures × a median of 8 rounds ≈ **38,000 comparison
   points**, against 4,788 if whole tournaments were compared.
2. **Localisation.** A divergence names one round of one tournament. The
   truncated TRF *is* the minimal reproducer, ready to promote into `tests/`.
3. **Independence.** Round *k* is judged on the declared history of rounds
   1..*k*−1, so one engine's mistake in round 3 does not cascade into a
   spurious divergence in rounds 4 through 9.

Round 1 (*k*=1, no results at all) is included and is not a special case: every
fixture carries record `152`, so the initial colour is pinned for both engines.
It is the round where a colour-model divergence shows up most cleanly.

## 4. Outcome model and classification

Each engine, for each `(fixture, round)`, returns exactly one of:

| outcome | meaning |
|---|---|
| `PAIRED(pairs, pab)` | a pairing was produced |
| `NO_LEGAL_PAIRING` | the engine states no legal pairing exists (bbp exit `1`) |
| `ERROR(code, message)` | anything else |

`PAIRED` is normalised to a canonical form before comparison: `pairs` is a
frozenset of `(white_startno, black_startno)` and `pab` is the starting rank
receiving the pairing-allocated bye, or `None`. Board order is *not* part of
this form — see below.

Comparing the pair of outcomes gives one of six classes:

| class | condition |
|---|---|
| `MATCH` | both `PAIRED` with identical pairs, colours and PAB; or both `NO_LEGAL_PAIRING` |
| `COLOUR` | both `PAIRED`, same unordered pairings and same PAB, but at least one board has the colours reversed |
| `PAIRING` | both `PAIRED`, different unordered pairings or different PAB |
| `PAIRABILITY` | one `PAIRED`, the other `NO_LEGAL_PAIRING` |
| `INCONCLUSIVE` | either returned `ERROR` |
| `SKIPPED` | screened out before the run (§6) |

`COLOUR` is separated from `PAIRING` deliberately: they implicate different rule
families (C.04.3 E versus the bracket and matching rules), and mixing them would
bury a small number of serious pairing divergences under a larger, more easily
explained colour population.

`INCONCLUSIVE` is quarantined and counted as neither agreement nor divergence. A
run whose inconclusive count is not near zero is not reporting on pairing at
all, and the report should say so prominently rather than quoting an agreement
rate over a shrunken denominator.

**Board order is a secondary, non-blocking dimension.** bbpPairings' output
order comes from its own `sortResults`, which is a presentation ordering rather
than a claim about C.04 board assignment. Record the comparison, report it in
its own table, and do not gate on it.

## 5. The truncation transform

`trftrunc.truncate(trf_text, keep_rounds) -> trf_text`

This is the only piece of real engineering in the project, and the only one that
can manufacture false divergences **on both sides at once**, so it gets its own
unit tests and its own validation gate (§7 step 4).

What it must do:

1. Cut each `001` line to `line[: 89 + 10*keep_rounds]`, dropping the round
   blocks for rounds after `keep_rounds`.
2. **Recompute the points field** `[80:84]` from the surviving results under the
   file's point system. bbpPairings refuses a file whose declared scores do not
   reconcile, so a stale points field is a hard stop, not a subtle skew.
3. **Recompute the rank field** `[85:89]` from the recomputed points.
4. **Leave record `142` at the original round count.** Baku acceleration and
   several C.04 provisions depend on the number of rounds the tournament is
   *scheduled* for, not on how many have been played. Rewriting `142` to
   `keep_rounds` would quietly change the pairing both engines should produce.
5. Leave `152`, `192`, `162`, `250` and `260` untouched.
6. Filter any per-round records to rounds ≤ `keep_rounds`. The present corpus
   carries none of these (no `240`, `300`, `320`, `330`), but the transform
   should handle them rather than assume their absence, since the corpus README
   lists them as records a future fixture set may add.

Points 2 and 3 need the score system. Read it the way the engine does rather
than reimplementing it — the cleanest source is this repository's own TRF
reader, so the transform stays correct if the score rules are ever revised.

## 6. Architecture

```
tests/interop/
  README.md                  what the sweep is, how to run it, how to triage
  engines/
    base.py                  Engine protocol, Outcome types, registry
    tiebreakserver.py        in-process adapter over commonmain
    bbppairings.py           subprocess adapter, pinned v6.0.0
  trftrunc.py                the truncation transform
  test_trftrunc.py           its unit tests
  normalize.py               canonical Outcome form
  runner.py                  corpus sweep -> results.jsonl
  report.py                  classification, summary, reproducer extraction
  divergences.json           accepted divergences, grouped by reason
  test_interop.py            pytest entry; skips when the binary is absent
```

### 6.1 The engine interface

```python
class Engine(Protocol):
    name: str
    version: str

    def screen(self, case) -> str | None:
        """None if this engine can handle the fixture, else the reason it cannot."""

    def pair(self, trf: str, round_no: int) -> Outcome:
        """Pair round `round_no` of a TRF truncated to rounds 1..round_no-1."""
```

Adding an engine is a module plus a registry entry. Everything else is
engine-agnostic.

### 6.2 The adapters

**`tiebreakserver.py`** runs in-process, exactly as `tests/corpus/_harness.py`
already does: import the engine modules once per worker and drive
`commonmain.common_main` with a synthesised `sys.argv`, so the real
read → prepare → pair path is exercised rather than a reimplementation of it.
Invoke as `-p -n <round>` and read `pairingResult[0]["pairs"]`, which is the
array of `(white, black)` competitor ids with `0` marking the PAB.

**`bbppairings.py`** shells out to the pinned binary, writes the truncated TRF to
a per-process scratch file (the `_harness.py` `_scratch()` pattern, so xdist
workers cannot clobber each other), and maps the exit code onto the outcome
model: `0` → parse the pairing file, `1` → `NO_LEGAL_PAIRING`, anything else →
`ERROR`. It must enforce a per-invocation timeout and treat a timeout as
`ERROR`, so one pathological fixture cannot hang a shard.

### 6.3 Register `-x weighted` as a second variant

bbpPairings always pairs by weighted matching. This repository has both its
default path and an `-x weighted` mode. Registering that mode as a second
variant of the same engine costs one registry line and directly addresses the
question of whether the two implementations follow the same priorities: a
divergence that disappears under `-x weighted` has a very different diagnosis
from one that survives it. The runner should therefore take a list of engine
variants, not a pair of engines.

### 6.4 Screening is declarative, never a crash

`bbppairings.screen()` returns a reason for the team category, for record `299`,
and for any unsupported `192` value — decided by inspecting the fixture, not by
running the binary and interpreting a failure. Two things follow: an unexpected
rejection stays visible as an `ERROR` instead of being absorbed into a skip, and
the report can state the coverage gap in the engine's own words:

> 4,788 of 5,000 individual fixtures compared. 212 excluded: bbpPairings does
> not support record 299 (abnormal assignment points).

That excluded count is itself a metric to watch across corpus regenerations.

## 7. Order of work

1. **Provision the binary.** Download the pinned tarball, verify the SHA-256
   from §2.1, extract. Confirm the v6.0.0 binary's record handling matches §2.2
   with a handful of hand-made probes — one team fixture, one carrying `299`,
   one `FIDE_DUTCH_BAKU` — before trusting the screening rules.
2. **`trftrunc.py` and its unit tests.** Column arithmetic, points and rank
   recomputation, `142` preservation, `keep_rounds == 0`, and the full-length
   case where truncation is the identity.
3. **Engine protocol, both adapters, normalisation.** Prove a single fixture
   end to end through both engines before scaling up.
4. **Validate every truncation, using this engine as its own oracle.** This
   engine's `-c` mode already replays a whole tournament and reports its
   prescribed `pairs` for each round. For every fixture and round, that
   prescribed pairing must equal what `-p` produces on the truncated file. Any
   mismatch is a bug in the transform, not a finding. **Gate on this before a
   single bbpPairings divergence is believed** — it validates all ~38,000
   truncations at the cost of one extra in-process run per fixture, and it is
   the difference between a divergence list worth triaging and one worth
   discarding.
5. **Runner and report.** First full sweep; classify what comes out.
6. **CI workflow.** Sharded and scheduled, modelled on the existing corpus job.

Steps 2 and 4 are the bulk of the work. The rest is small.

## 8. Running it

There is no macOS binary and building from source is out of scope, so the sweep
runs on Linux in both of these:

**Local iteration — Docker on any host.** Debugging a divergence through CI
round-trips is not workable, so the local loop must exist:

```
docker run --rm -v "$PWD:/w" -w /w python:3.12-slim \
  sh -c 'pip install -q -r requirements.txt -r requirements-dev.txt &&
         tests/interop/fetch-bbppairings.sh &&
         pytest tests/interop -n auto'
```

The fetch script downloads and checksum-verifies the pinned release; it is the
same script CI uses, so the two cannot drift.

**Full sweep — GitHub Actions.** A new workflow, `workflow_dispatch` plus a
nightly or weekly schedule, sharded across runners. `.github/workflows/tests.yml`
already has the shape to copy: an 8-way matrix, `TIEBREAK_CORPUS_SHARDS` /
`TIEBREAK_CORPUS_SHARD` round-robin partitioning, `-n auto` within each runner,
artefact upload, and a summary job that refuses to report a pass over an
incomplete set of shards. The interop sweep should reuse the partitioner rather
than grow a second one.

Keep this sweep **out of the pull-request `tests` workflow**. It depends on an
external download and reports on an independent implementation's behaviour; a
bbpPairings quirk should not turn a pull request red. Schedule it, and let it
raise its own signal.

## 9. Output and triage

The runner writes `results.jsonl`, one record per `(fixture, round, variant)`,
each carrying both outcomes, the class, the corpus fixture name, the round, and
the pinned engine version and binary checksum — so any report can be traced back
to exactly what produced it.

`report.py` produces a Markdown summary:

- total comparisons, and the screened-out count with its reason
- agreement rate, with the inconclusive count stated separately and never folded
  into the denominator silently
- divergences by class, with counts
- the divergent cases grouped by shape — same bracket size, same round number,
  same colour situation — because 38,000 comparisons producing 400 divergences
  will not be 400 distinct causes, and grouping is what turns a list into a
  finding
- for each group, one minimal reproducer written to disk: the truncated TRF,
  both outcomes, and bbpPairings' `-l` checklist for that round

**Triage discipline mirrors `known_failures.json`**, whose rule
`tests/corpus/README.md` states plainly and which applies here unchanged:
regeneration is not re-baselining. Every entry in `divergences.json` is
classified by hand, grouped by reason, into exactly one of:

| verdict | action |
|---|---|
| `tiebreakserver` is wrong | fix the engine; the reproducer becomes a test under `tests/` |
| `bbppairings` is wrong | record with the C.04 citation that settles it; report upstream |
| `underdetermined` | C.04.3 admits both pairings here and the two engines choose differently |

Expect the third class to be non-empty, and treat it as the interesting one: a
case where the rules do not determine a unique answer is worth writing down
whichever engine you prefer, because it is a fact about the rules rather than
about either implementation.

## 10. Risks

| risk | handling |
|---|---|
| a truncation bug manufactures divergences on both sides | step 4's self-validation gate, before any triage |
| the corpus is regenerated with `FIDE_DUTCH_2026`, which the pinned v6.0.0 rejects | screening reports it as a coverage collapse rather than a silent skip; note the constraint in the corpus generator |
| a pathological fixture hangs the binary | per-invocation timeout in the adapter, mapped to `ERROR` |
| divergences are numerous and shapeless | group by shape in the report; triage groups, not rows |
| the excluded 212 `299` fixtures hide a real defect | they remain covered by the existing corpus suite; the exclusion is stated in every report, not buried |
