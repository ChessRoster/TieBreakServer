# FIDE pairing and tie-break conformance corpus

This directory contains complete, self-contained tournament fixtures for testing
FIDE Dutch individual pairing (C.04.3), FIDE Swiss team pairing (C.04.6), and
C.07 tie-break calculations.

## Files

```
tests/corpus/
  corpus.jsonl.gz            gzip-compressed JSON Lines fixture data
  known_failures.json        active expected failures, grouped by reason
  _harness.py                corpus loader and in-process checker driver
  test_corpus.py             pytest entry point
  regen_known_failures.py    expectation regeneration tool
```

## Corpus contents

The corpus contains 6,000 TRF-2026 tournaments:

| category | valid | invalid | total |
|----------|------:|--------:|------:|
| Individual | 4,281 | 719 | 5,000 |
| Team | 435 | 565 | 1,000 |
| **Total** | **4,716** | **1,284** | **6,000** |

Each decompressed line is one JSON object:

```json
{"name": "ind_00000", "category": "individual", "valid": true,
 "skip": false, "skip_reason": null, "trf": "062 45\n072 45\n001 ..."}
```

| field | type | meaning |
|-------|------|---------|
| `name` | string | unique fixture identifier and pytest test id |
| `category` | string | `"individual"` or `"team"` |
| `valid` | bool | expected checker verdict |
| `skip` | bool | whether the fixture is excluded from the run |
| `skip_reason` | string or null | reason for an exclusion |
| `trf` | string | complete TRF-2026 file text |

No current fixture is skipped. The `skip` fields remain part of the format so a
consumer can stage future additions when necessary.

The fixtures cover field and team sizes, board and round counts, draws,
forfeits, byes, Baku acceleration, non-default score systems, prohibited
pairings (record 260), abnormal assignments (record 299), Type A and Type B team
colour models, match-point and game-point primary scoring (record 192), and the
individual and team tie-break catalogues (record 212).

## Verdict semantics

`valid` is an identity verdict, not a general quality score. A fixture is valid
when every declared pairing agrees board-for-board and colour-for-colour with
the pairing prescribed by the engine, and every declared rank agrees with the
ranking calculated from its declared tie-breaks. An invalid fixture deviates
from at least one of those prescribed results.

TRF records the declared ranking but does not carry golden numeric tie-break
values. The corpus therefore detects a tie-break calculation error when it
changes that ranking; it cannot detect an incorrect intermediate value that
leaves the final order unchanged. The reader separately checks that declared
score totals reconcile with the recorded results and score system.

Most deliberately invalid fixtures begin as valid tournaments and then receive
one isolated change. The fixture name records the mechanism:

| mechanism | category | change |
|-----------|----------|--------|
| `c1` | individual | repeat pairing |
| `c2` | individual | second pairing-allocated bye for an ineligible player |
| `c3` | individual | pairing of two players with the same absolute colour preference |
| `team_colour` | team | reversed board colours in one match |
| `team_opponent` | team | cross-swapped opponents in two matches |
| `team_rank` | team | swapped final ranks for two teams |

265 further team fixtures are invalid for a reason that was not designed in. They
were generated by this engine before the C.04.6 corrections, so they declare the
pairing it used to produce; the corrected engine does not produce it, and by the
rule above that makes them invalid. See "Fixtures the corrections outdated".

The corrupted files remain parseable and internally consistent; the intended
failure is the mismatch with the prescribed pairing or ranking. These six
mechanisms account for every invalid fixture in the corpus.

## Running the tests

The harness writes each embedded `trf` value to a temporary file and drives the
same `common_main` pipeline as `pairingchecker.py` and `tiebreakchecker.py`. It
checks that the tie-break path does not fault and that the combined pairing and
standings identity verdict agrees with `valid`.

By default pytest selects a deterministic sample of about 500 records:

```bash
pytest tests/corpus/ -n auto
```

Set `TIEBREAK_CORPUS_FULL=1` to run all records:

```bash
TIEBREAK_CORPUS_FULL=1 pytest tests/corpus/ -n auto
```

CI runs the complete corpus in round-robin shards. `TIEBREAK_CORPUS_SHARDS`
sets the number of shards and `TIEBREAK_CORPUS_SHARD` selects the zero-based
shard index. Once every runner finishes, CI posts or updates one pull-request
comment with the combined results; the same report remains available on the
workflow run's summary page.

`known_failures.json` holds the records whose disagreement with the engine has
not yet been accounted for, under strict `xfail` markers, so a fixed one becomes
an XPASS and fails the suite until its expectation is removed. **It is currently
empty**: every record executes and is expected to pass. After an engine change,
regenerate it with:

```bash
python3 tests/corpus/regen_known_failures.py
```

Review and classify every new disagreement rather than treating regeneration as
an automatic re-baseline: the tool writes the new names under a single
"unclassified" reason, and they are not fit to commit until each one has been
traced to a cause and moved under a reason that names it. The next section is
what that looks like when it has been done.

## Fixtures the corrections outdated

The 6,000 fixtures were generated by this engine, so a fixture's declared pairing
is whatever the engine produced on the day it was written. Correcting the engine
therefore moves fixtures out of agreement with it, and the record that is now
wrong is the fixture, not the answer. 303 records were in that position after the
C.04.6 corrections. None of them is carried as an expected failure: an `xfail`
asserts that the engine gets a record wrong, which is the opposite of what
happened.

No input was changed. Every field - players, ratings, teams, boards - is as it
was generated. What changed is 38 files by one line, and 265 expectations.

**38 records carried a scoped record 299.** The record gives an abnormal result a
value, scoped to one round and to named competitors, that differs from the score
system's. The reader refuses such a file rather than scoring the tournament by
rules it did not ask for, so the assignment is dropped and the rest of the file
reads as it always did. These stay valid and pass.

**265 records declare a pairing the corrected engine does not produce**, so by the
rule in "Verdict semantics" they are no longer valid, and that is now what they
say. 211 of them have the engine choosing different pairs; 19 declare a round
with no legal pairing at all, handing out two or three pairing-allocated byes
where art. 1.4 has one to give; the remaining 35 differ in colour or carry a
record 299 as well.

### Why none of them could be repaired in place

In a Swiss system a round's output is the next round's input, and that closes off
every patch smaller than regenerating the tournament:

* where the engine picks **different pairs**, every result after that round
  describes a game that would not have been played;
* where it picks only **different colours** - which looks local, and is not - the
  colour history feeds the colour preferences of art. 1.7, so correcting round 2
  moves the pairing of round 3.

Only the record 299 line is inert enough to remove, which is why 38 could be
repaired and 265 could not.

Regenerating them would need a corpus builder. The one that produced these
fixtures is in neither this repository nor the generator's: nothing in either can
write a record 310 carrying real match and game point totals, which every team
fixture here has. Until that is rebuilt, the 265 test that the engine rejects a
stale pairing rather than that it agrees with a good one - which still executes
and still catches a regression, in the other direction.

## Fixtures the corrections outdated

The 6,000 fixtures were generated by this engine, so a fixture's declared
pairing is whatever the engine produced on the day it was written. Correcting
the engine therefore moves fixtures out of agreement with it, and the record
that is now wrong is the fixture, not the answer. 303 records are in that
position and are listed in `known_failures.json` under the three reasons below.
Every one of them is accepted by the engine as it stood at commit `9c19600`, the
last state the corpus was generated from, and each group's cause was isolated by
putting only that correction back.

### The pairing identifier and the first-team (244 team records)

Two corrections move these:

* **art. 3.6.1**: "the smaller-TPN player is the top member, the larger-TPN
  player is the bottom member". The engine ranked a pair by each team's position
  in the bracket instead, and it numbered the bracket in the order it was handed
  in, which is score order: residents came before upfloaters whatever their TPNs
  were. Which team is the top member is what art. 3.6.2 builds the identifier
  out of, so every heterogeneous bracket could be identified wrongly.
* **art. 4.2.1**: the first-team is the team with the higher *primary score*.
  The engine used to compare the accelerated score, which is the primary score
  plus the virtual points of C.04.7 art. 1.4. The two are the same number
  outside an accelerated tournament, which is why only the Baku fixtures see it.

Restoring one correction at a time accounts for every record:

| put back | records restored |
|----------|-----------------:|
| art. 3.6.1 alone | 189 |
| art. 3.6.1 and art. 4.2.1 together | 33 |
| art. 4.2.1 alone | 22 |
| **total** | **244** |

`tests/test_pairing_fideteam_corpus_cases.py` derives the art. 3.6.1 case by
hand from `team_0018` round 3, so the identifier order is pinned by a test that
does not depend on the corpus.

### An impossible round (19 team records)

These fixtures end with a round the engine used to fabricate. When no legal
pairing existed it fell back on pairing as many teams as it could and handing a
bye to everyone left over, and that fabricated round is what the fixture
declares. One bye is all a round has to give, and only when the field is odd:
art. 1.4 says "should the number of players to be paired be odd, one player is
not paired", and art. 3.3.1 completes a round-pairing when all teams "except at
most one, which receives the PAB" have been paired. Every one of the 19 declares
two or three byes in the one round -- `team_0002` is a field of seven teams
whose round 6 hands byes to three of them. Beyond the count, 14 of the 19 give a
team a second pairing-allocated bye, which art. 2.1.2 [C2] forbids outright, and
the other five give byes in an even field, which has none to give.

The engine now reports the round as unpairable instead, with status 505. Art.
3.3.3 leaves it there: "if impossible, the Chief Arbiter decides". The message
cites C.04.3 art. 1.9.3, which says the same thing, because the code that raises
it is shared with the individual systems.

That verdict was checked independently of the engine. For each of the 19, the
teams' own declared match list was replayed up to the failing round, and every
way of splitting the field into pairs, plus one bye where the field is odd, was
enumerated under art. 2.1 [C1] and [C2] alone. No legal pairing exists in any of
the 19. `tests/test_unpairable_position_reports_cleanly.py` pins the reporting
path.

### A scoped record 299 (35 individual and 5 team records)

Each of these files carries a record 299 that gives an abnormal result a value,
scoped to one round and to named competitors, and that value differs from the
one the file's own score system gives that result. The reader has never applied
a scoped assignment; it used to drop the record and score the tournament by the
score system, which is how the fixtures came to declare the scores they declare.
It now refuses the file instead, because scoring a tournament by rules its file
did not ask for is worse than saying the file cannot be read. Stripping the 299
line from these fixtures makes 38 of the 40 agree with the engine again; the
remaining two, `team_0558` and `team_0570`, are team records that also carry one
of the pairing differences above.

Five more fixtures carry a record 299 that fires and are refused for it:
`ind_04469_inv_c1`, `ind_04627_inv_c3`, `ind_04940_inv_c1`,
`team_0874_inv_team_colour` and `team_0983_inv_team_opponent`. They are not
listed in `known_failures.json` because they are the deliberately invalid
fixtures of the table above: the corpus expects them to be rejected, and being
refused at the reader is still a rejection. They appear only in the value
baseline, whose 45 changed rows are these five and the 40 above.
